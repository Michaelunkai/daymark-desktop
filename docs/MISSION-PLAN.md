# Daymark AI Companion App — Full Mission Plan

## 1. MISSION OVERVIEW

This mission is the completion and perfection of one single application on one physical phone: the "Daymark AI" companion app. This is the AI control panel application — the Android package whose identifier ends in the suffix `.companion`, whose launcher name shown on the phone's home screen is "Daymark AI", and whose main entry screen is the AI workspace activity known internally as AiWorkspaceActivity. It runs on the user's Samsung phone, model SM-S938B, which is connected over wireless debugging. Its wireless debugging serial begins with the characters `adb-R5CY610XJGV`. Everything in this document concerns that phone and that one app and nothing else.

The single most important rule of this entire mission is the app-identity lock. There was once a family of similarly named applications installed on this phone, and that family caused repeated, costly confusion in past working sessions. The family consisted of: the normal Daymark tasks application (a completely different, unrelated product — a personal task manager that must never be opened, modified, built, installed, or tested during this mission); an `.ai` variant package; a `.verification` variant package; and the `.companion` AI control panel application, which is the sole subject of this mission. Because these packages shared naming fragments, past sessions repeatedly installed, launched, or verified the wrong one, wasting hours and producing false test results. Commands intended for one app landed on another; a test was recorded as passing against an app that had never received the change; a build was installed over the wrong package and silently clobbered it. That problem has already been solved at the source: all of the wrong variants were uninstalled in a completed earlier phase. The normal Daymark tasks app remains on the phone as a separate product that this mission must treat as radioactive — it is simply not part of this mission's universe.

What remains, and what this mission touches, is exactly one application: the companion AI app. But the removal of the duplicates is not by itself a permanent safeguard. Old commands, stale scripts, muscle memory, and ambiguous log output can all pull a future session back toward the wrong package. The identity lock must therefore be re-verified actively, on every single build, install, launch, and test cycle, for the rest of the mission. Before any action is taken against the phone, the working session must confirm, using live on-device evidence, that the package it is about to interact with is the companion package. That means listing the installed packages and confirming the companion identifier is present and that the removed variants are absent, and checking which application is in the foreground after any launch, and confirming the foreground application is AiWorkspaceActivity belonging to the companion package. Only after those checks pass may a build be installed, a screen be interacted with, or a result be recorded. If any identity check fails or is ambiguous, the session stops and re-establishes identity before proceeding. This is not bureaucracy; it is the lesson of every past failure on this project, written down as law.

With the identity lock understood, the mission itself can be stated plainly. The companion app is already functional at a baseline level: it pairs, it syncs, it draws the board, it runs AI sessions. The infrastructure beneath it has just been rebuilt from the ground up — the backend now lives in the user's own cloud account, it can no longer fill up and fail, and the app has been re-signed with a newly created and properly escrowed key. What remains is the perfection work, organized in this document as five pillars of new or corrected capability, followed by a complete audit of every screen and control, all executed under a strict build-and-verify discipline and a set of non-negotiable operating rules.

The five pillars, described in full detail in section 4, are: bringing the NVIDIA provider to exact parity with the user's desktop IDE, including a rotating pool of eleven API keys and exactly five fixed models; giving the Z.AI provider a dual mode — coding-plan subscription and metered API key — with instant automatic failover between modes and across providers; guaranteeing live, specific, human-English progress lines for every running session on every provider at least once per minute; making the OpenCode model list truthful, sourced live from the service so phantom models can never appear; and adding a Delete All control for the Finished column that clears dozens of completed tasks in under one second with zero collateral damage.

The success condition for the whole mission is simple to state and strict to meet: every pillar's acceptance tests pass on the real phone, every screen and control in the application has been exercised and passes with evidence, all of it proven by on-device observation rather than source-level reasoning, and each phase's changes have been seen landing live on the phone by the user. Nothing less counts as done.

A note on how to read this document. Sections 2 and 3 are the ground truth of what exists: what already happened, and how the app works today. Section 4 is the build list, and each pillar within it follows the same internal shape — goal, exact behavior demanded, how the app works after the change, and acceptance tests with concrete numbers — so that any competent engineer can implement and verify the pillar from the words alone. Sections 5, 6, and 7 define the audit, the delivery mechanics, and the rules of engagement. Section 8 gives the execution order that ties the phases together with explicit gates.

## 2. WHAT ALREADY HAPPENED (COMPLETED FOUNDATION)

Everything in this section is finished work. It is recorded here because the pillars build directly on it, and because understanding why the infrastructure was rebuilt explains several rules that later sections enforce.

The first completed piece of work was the removal of the duplicate applications. The `.ai` variant and the `.verification` variant were uninstalled from the phone, leaving only the companion AI app and the unrelated normal Daymark tasks app. After the removal, the surviving companion app was opened on the phone and verified to be healthy: it displayed live board data from the real workspace, and its pairing key was intact, meaning the app's link to its backend survived the cleanup untouched. This closed the identity-confusion era permanently, provided every future session re-verifies identity as section 1 demands.

The second completed piece was the discovery and diagnosis of a terminal failure in the original backend. The companion app had been syncing against a third-party hosted service. During earlier sessions that service began rejecting every write. Reads continued to work perfectly — the app could pull the whole workspace without error — but every attempt to push a change returned a server error. Investigation traced the failure to growth without limits. The workspace had grown to nearly nine hundred twenty tasks. The server held over a thousand sync tombstones — deletion markers that exist so other clients learn that a task was removed, and which this service retained forever, so that years of deleted tasks accumulated as permanent records of things that no longer existed. Worst of all, the service stored a saved-state history of the workspace on every write, and that change-history storage grew without any pruning mechanism at all. Every completed task, every progress line, every reorder, every preference tweak added another full saved state to the history, and nothing ever removed one. Eventually the storage layer hit its limit and began throwing an error on every write attempt. No amount of retrying from the client could fix this; the server itself was full and had no self-cleaning behavior. The failure mode was especially insidious because the app's read path stayed healthy the whole time — the board kept rendering, pulls kept succeeding — so the app looked alive while being, for all practical purposes, unable to record anything new. The backend was dead for writes while pretending to be alive for reads.

The third completed piece was the decision and full execution of a backend migration to the user's own Cloudflare account. The reasoning was straightforward: a backend the user does not control is a backend that can die without warning and cannot be repaired when it does, and this one had demonstrated exactly that. The migration copied the identical server program — the same logic, the same API shape, the same behavior — and deployed it as a new worker on the user's Cloudflare account, backed by a fresh, empty database. Then the entire live workspace state was seeded into that fresh database at the exact same revision number the phone had already seen. This detail mattered enormously: the revision number is the coordinate that tells a syncing client where it is in the workspace's history. Because the seeded revision matched the phone's current revision exactly, the phone app did not see the migration as a data event at all. Its next poll lined up with the new server's state perfectly, and it continued syncing seamlessly as if nothing had happened — no duplicate entries, no replayed changes, no lost state, no re-pairing.

To prevent the new backend from ever dying the same death as the old one, an automatic history-pruning rule was added to the new deployment: for every workspace, only the twenty most recent saved states are retained, and older saved states are deleted automatically as new ones are written. The storage footprint therefore reaches a fixed ceiling and stays there forever. Twenty retained states is far more than any client needs for catch-up, since clients sync by revision rather than by replaying history. The class of failure that killed the original backend — unbounded change-history growth — is now structurally impossible on the new infrastructure, not merely unlikely.

The fourth completed piece was switching the phone app's sync host to the new address, so all of its pull and push traffic now flows to the user's own worker instead of the dying third-party service. This was a configuration-level change inside the app, shipped with a rebuild, and confirmed by observing the app's traffic and sync behavior against the new endpoint.

The fifth completed piece was the signing-key recovery. During the migration the app needed to be rebuilt and reinstalled, which raised the question of the signing keystore. Inspection of the original escrow directories on the Windows machine found them empty — the keystore that had signed the previously installed app was gone, and no copy existed anywhere it was supposed to be. A signature mismatch between a fresh build and the installed app proved conclusively that the old signer was lost; an app signed with a different key cannot be installed over the top of the old one without a full uninstall. Rather than fight this, a brand-new app signing keystore was created, and it was escrowed in three separate locations so that losing a single copy — or even two — can never again strand the project. The app was rebuilt with the new keystore, reinstalled on the phone as a fresh install (which the signature mismatch had anyway forced), and its pairing key was restored from backup so the fresh installation immediately reattached to the live workspace with all its history and cards intact.

The sixth completed piece was live verification of the whole migrated stack, performed on the real phone. Pulls succeed: the app draws the full workspace from the new backend, cards and columns rendering with real data. Pushes confirm: a write from the app returns an explicit success status from the new worker, closing the loop in the direction that killed the old service. The agent token — the credential the app uses for its automated writes — re-mints automatically when needed, so authentication never becomes a manual chore. The infrastructure picture at the end of the foundation phase is therefore this: the backend is owned by the user, its storage is pruned automatically and can never fill up, the app is signed by a keystore that exists in three escrow copies, and the live sync loop is proven healthy in both directions. Every pillar in section 4 assumes this foundation and builds on top of it.

## 3. HOW THE APP WORKS (ARCHITECTURE IN WORDS)

This section describes the companion app as it exists today, in plain words, so that every later requirement lands on understood ground.

The companion app is a native Android control panel that mirrors an entire remote workspace onto the phone screen. Its connection to the backend is a sync service with two halves. The first half is a full pull: when the app starts or reconnects, it fetches the entire workspace document in one operation. That document contains everything — the projects, the sections within projects, the tasks within sections, the notes, the order items, the diary entries, and the workspace preferences. The app holds this document locally and renders its interface from it, so the phone screen is always a projection of one authoritative remote document rather than a database of its own. The second half is a long-poll loop: after each pull, the app asks the server whether anything has changed and holds that request open until either a change arrives or a timeout elapses, then immediately re-pulls whatever changed and asks again. The result is a near-live mirror: when a task changes anywhere — from the phone, from a desktop tool, or from an AI agent writing into the workspace — the phone reflects it within moments, without the user refreshing anything. When the network drops, the loop retries with backoff, and when connectivity returns the app catches up by pulling forward from its last known revision. Losing the connection never corrupts anything, because the local copy is always disposable: the remote document is the only truth, and the app rebuilds its view from it on every catch-up.

The central screen, AiWorkspaceActivity, draws the workspace as a board with three columns: To do, In Progress, and Finished. Every card on the board is a task, and in this app's vocabulary every task is called a session, because each one typically represents a unit of AI work being tracked from start to finish. Cards move between columns as their status changes, either by user action on the phone or by updates arriving through sync. The column a card sits in is derived from the task's status field, so a move is a data change, not a layout trick — which is why moves propagate everywhere and survive restarts. A card shows its title, its column-appropriate action controls, and its live status line, drawn from the journal as described below.

The description field of each session works as a journal. New lines are prepended at the top of the description, so the newest entry is always the first thing visible, both in the raw data and on the card face. Each line carries a marker classifying what kind of entry it is — markers such as update, progress, heartbeat, message, order, ack, and reopened — followed by the line's content and a wall-clock stamp recording when it was written. The wall-clock stamp is written by the writer of the line and displayed on the card, so the user can tell at a glance not only what last happened but how long ago. Over the life of a session this journal becomes a complete narrative of what happened, who or what acted, and when — and because it lives in the description, it syncs everywhere the task goes, including to desktop tools and agents that read the same workspace.

The app contains a parser that reads each journal line and classifies it by its marker and shape. This classification drives what the card displays. The parser deliberately ignores machine-written watchdog lines when choosing what to feature — the watchdog emits regular heartbeat lines to prove a session is being monitored and has not silently died, but those lines carry no human meaning and would drown out real information if shown as the card's headline. After filtering, the card shows the newest session-authored line as its live status. This is why progress lines matter so much in this mission: the line an AI session writes into its journal is, literally, what the user sees on the card as the session's current state. A stale line means the card looks stale. A generic line means the card looks useless. A missing line means the card looks dead. The parser's filtering rules are therefore not a cosmetic detail; they are the lens through which all of Pillar C's output reaches the user.

The watchdog itself deserves a step-by-step description, because its behavior defines what "a session is alive" means. On its own interval, the watchdog examines every in-progress session it is responsible for. For each one, it checks the age of the newest journal line. If the line is fresh, the watchdog appends a heartbeat line stamped with the current time and moves on — the heartbeat is proof of observation, nothing more, and it is written so the parser can recognize and suppress it on the hero display. If the newest line is older than the expected freshness window, the watchdog treats the session as possibly stalled: it writes a heartbeat noting the staleness it observed, and it keeps watching on subsequent ticks so the record shows exactly when attention lapsed and when it resumed. The watchdog never changes a session's status, never stops a session, and never writes content pretending to be the session's own voice — it observes, stamps, and reports, and those three limits are what make its output safe to filter from the card face.

Tombstones deserve their own explanation, because deletion in a synced system is not the same as erasure. When a task is deleted — by the user, or by the Delete All flow in Pillar E — the server does not simply forget it. The task's identifier is recorded as a tombstone: a small marker saying this task existed and is now deleted, effective at this revision. Any client that later pulls changes sees the tombstone and removes the task from its own view instead of resurrecting it from a stale local copy. Without tombstones, a phone that had been offline would come back online, still holding the deleted task, and re-push it — the deleted card would haunt the board forever. Tombstones are the reason Pillar E's deletions propagate cleanly to every other reader of the workspace. The original backend's tombstone hoarding — over a thousand of them, never retired — is also a cautionary tale: tombstones are necessary but must be bounded, and the new backend is expected to retire them once every live client has acknowledged the deletion.

Conflicts deserve a worked description too, since the tester will be writing to the board at the same moment AI sessions are writing to it. Suppose the user renames a card on the phone while a session appends a progress line to the same card's journal at nearly the same instant. Both writers base their writes on the same prior revision. Whichever write reaches the server second carries a base revision that no longer matches the server's current one, and the server detects the mismatch instead of accepting blindly. It then merges by field: the rename touched the title, the append touched the description, the two changes do not overlap, so both are kept and the revision advances once. A true collision — two writers changing the same field — resolves by a deterministic rule the server applies identically every time, so every client converges on the same outcome rather than diverging. The phone then pulls the merged result and re-renders. From the user's seat, the visible behavior is simply that both actions survived and the board moved forward — no error, no lost line, no rollback of unrelated work.

The app is not only a mirror; it is also an actor. A built-in component called the progress broadcaster runs on a sixty-second timer. On each tick it walks every in-progress session in specific sections of the workspace and prepends a fresh progress line to that session's journal, describing what the session is doing right now. This is the mechanism that keeps cards visibly alive during long runs, and it is the mechanism Pillar C extends and hardens so that its coverage and its line quality are guaranteed rather than incidental.

All writes from the app — progress lines, status changes, new tasks, edits — go through a retry path. If a push fails, whether from a network hiccup or a transient server condition, the app retries rather than silently dropping the change; a write that eventually cannot land is surfaced as a failure, never as a false success. On the server side, concurrent edits are merged with conflict detection: each write carries the base revision it was made against, and if two writers change the same thing at the same time, the server detects the collision and resolves it deterministically instead of letting one write silently clobber the other. This is what makes it safe for the phone, desktop tools, and AI agents to write to the same workspace simultaneously — a situation that happens constantly during this mission, since the tester and the AI sessions act on the board at the same time.

The app also talks directly to AI providers to run sessions. It stores the user's provider selection — which provider and which model a session should run on — and it stores per-provider API keys. Key storage is hardened: keys are encrypted with strong AES encryption using keys rooted in the phone's hardware-backed keystore, the Android facility that generates and holds cryptographic material in hardware that cannot be extracted, even from a compromised operating system. Plaintext keys never touch persistent storage; a key exists in memory only for the moments it is being used to sign a request, and it is decryptable only on this phone, only by this app. This existing encryption path is exactly the path every new key introduced by the pillars — the eleven NVIDIA keys and the Z.AI metered key — must flow through, with no exceptions and no side doors.

When a provider imposes a rate limit, the app can detect it from the provider's error responses and automatically switch the affected session to a different provider so the work continues. Today that capability is basic; Pillar B turns it into a complete, ordered, journaled failover system.

Finally, a note on how the app proves activity to the outside world: the journal lines themselves are the evidence trail. When this mission's later sections demand verification "on device," a large part of that evidence is the set of visible, timestamped, marker-carrying lines on the session cards — lines that could only have been written by the behavior under test, stamped with the time it happened, and readable by anyone looking at the board.

## 4. THE FIVE PILLARS

### Pillar A — NVIDIA provider with a rotating key pool

Goal. Bring the NVIDIA provider inside the companion app to exact parity with the way it works in the user's Windows ZCode desktop IDE. After this pillar, using NVIDIA from the phone must feel identical to using it from the desktop: same endpoint behavior, same key pool depth, same resilience, and the same five-model lineup. The desktop IDE is the reference implementation; where the phone's behavior could differ, the desktop behavior wins.

Exact behavior demanded. The provider communicates with the NVIDIA API endpoint at integrate.api.nvidia.com, using the same request shapes and authentication style the desktop IDE uses, so that a request from the phone is indistinguishable from a request from the desktop apart from which key signs it. Authentication draws from a pool of exactly eleven API keys: eight keys taken from the user's multi-key file plus three keys taken from three single-key files living in the Windows credentials folder. The import is a one-time operation with a defined procedure: read the eleven keys from the Windows files in a fixed order — the eight multi-file keys first, in file order, then the three single-file keys — hand them to the app through an import flow, and confirm on the key-management screen that the count reads eleven. From the moment of import the keys exist only inside the app's existing hardware-keystore-backed AES encryption. No key may ever be written to plaintext storage, to logs, to exported files, to crash reports, or to any backup that is not itself encrypted. If a key is displayed anywhere in the interface, it is masked. The original Windows files remain where they are, untouched, as the desktop's own reference copies; the mission copies keys into the app, never moves them.

The rotation engine is the heart of this pillar. For each outgoing request to NVIDIA, the engine picks the next key in round-robin fashion — each request uses the following key in the pool relative to the last one used, so load spreads evenly across all eleven keys and no single key bears the brunt of heavy use. When a request fails because the key was rate-limited, or unauthorized, or the server returned an error, the engine instantly retries the same request on the next available key in the pool, without user involvement and without surfacing any error. The retry is of the same request with the same payload — a rate limit on one key says nothing about the request itself, so the request deserves to succeed on a healthy key. The engine distinguishes key failures from request failures: a malformed request, a network timeout, or a refused connection is retried on its own path and never burns a key's standing, while the three key-failure patterns — rate-limited, unauthorized, server rejection of the key — trigger rotation and cooldown. The rejected key is placed on a sixty-second cooldown: during that window the rotation engine skips it entirely, so no request is wasted on a key known to be failing. When the cooldown expires, the key is restored to active duty automatically, with no restart and no manual action. If the next key in rotation is also cooling down, the engine keeps stepping forward until it finds an active one, wrapping around the pool as needed. The user-visible contract is absolute: as long as any key in the pool still works, the user never sees a key failure. A total failure is shown only when every key is simultaneously rejected, and even then the message must describe the situation in plain terms — the key pool is exhausted, keys are cooling down and will recover — rather than leaking key material or raw provider errors.

The pool state must survive the app being closed and reopened. Cooldowns are short, but the keys themselves are permanent configuration; on every app start the engine reloads the encrypted pool, restores all keys to active (a sixty-second cooldown has certainly expired by the time a restart completes), and continues rotation from wherever the sequence left off. Rotation state is bookkeeping, not data; losing track of which key went last is harmless as long as the pool itself is intact. A partially completed import must also be safe: re-running the import with the same eleven keys produces a pool of eleven, not twenty-two — the import flow replaces or reconciles rather than blindly appends.

The model lineup is fixed and exact. The NVIDIA provider exposes exactly five models, in this exact order, with the first as the default: GLM five point two by Z.ai — a large mixture-of-experts coding model, and the default selection for the provider; Nemotron three Ultra, the five hundred fifty billion total parameter model; Nemotron three Super, the one hundred twenty billion parameter model; DeepSeek version four Flash; and a fifth model called Inkling, from Thinking Machines. The model picker must show exactly these five under the NVIDIA provider chip and never a sixth. This is a hard constraint, deliberately different from Pillar D's philosophy: NVIDIA's list is curated and frozen by this mission, not discovered live, because the user has verified these five and wants nothing else in the way. No dynamic discovery may add models to this list, and no leftovers from earlier experimentation may remain. The order is the display order, and the first entry is what a new session gets if the user does not touch the picker. Any existing sessions still pointing at a removed model migrate to the default rather than failing.

A key-management screen completes the pillar. It shows the user how many keys are currently loaded — the number eleven when fully stocked — and the current state of each key: active or cooling down, with the remaining cooldown visible if practical. Keys are always masked; the screen may show, at most, a short non-identifying fragment such as the final characters, or preferably only a positional label like key one through key eleven. The screen allows adding keys and removing keys. Adding a key routes it through the same hardware-keystore encryption as the import flow, and the new key joins the rotation immediately. Removing a key takes it out of rotation immediately and permanently, and the rotation engine must handle the shrinking pool gracefully, including the extreme cases of one remaining key (the pool degenerates to a single key with normal cooldown behavior) and zero remaining keys (the provider reports honestly that it has no keys and cannot run sessions, without crashing and without pretending).

How it works after the change. The user opens the provider chip, selects NVIDIA, sees exactly five models with GLM five point two by Z.ai preselected, and runs a session. Under the hood, every request rotates to the next key. When one key gets rate-limited mid-session, the very next attempt goes out on a different key; the session's journal shows the work continuing, and the only trace of the failure is at most a progress line noting the provider recovered from a key rotation — never an error dialog. The key-management screen, opened at any moment, shows eleven keys mostly active with any recently rejected keys cooling down and returning to active on their own.

Acceptance tests, with concrete numbers. First: a new task is created and run successfully on each of the five NVIDIA models, one run per model, producing five of five successful completions, each evidenced by its journal lines and a finished card. Second: a mid-run model switch — the session is started on one NVIDIA model, switched to a different NVIDIA model while running, and the session must stay alive and complete, with the journal recording the switch. Third: a forced rate-limit is applied to one key (the key is deliberately driven into a limited state, or its requests are made to fail in the rate-limit pattern), and the test proves silent failover: the running session continues on another key with no user-visible error, and the key-management screen shows the rejected key in cooldown. Fourth: automatic recovery — after the sixty-second cooldown expires, the previously rejected key returns to the active state on the key-management screen and is used again by the rotation engine, proven by observing it serve a subsequent request.

Each test also carries defined edge cases and a defined evidence set. For the five-model run, the edge cases are: a run started with no manual model choice must land on GLM five point two by Z.ai by default, and a run of the same model twice in a row must succeed equally — the rotation engine must not behave differently on repeat runs. Evidence per model: the card's journal showing start, progress, and completion lines naming the model, plus a screenshot of the finished card. For the mid-run switch, the edge case is switching early, seconds after start, and late, near completion — both must survive; evidence is the journal's switch line plus completion. For the forced rate-limit, the edge cases are: the limited key must not be retried during its cooldown even under heavy request volume, and the failover must be silent — the evidence is the runtime log from the app's own tag showing the rotation decision, the key screen showing the cooldown state, and the absence of any error dialog on screen. For recovery, the edge case is that the recovered key rejoins rotation in its original pool position rather than jumping the queue; evidence is the key screen's return to active plus a later request served by that key, visible in the log sequence.

### Pillar B — Z.AI dual mode with instant failover

Goal. Let the user run Z.AI sessions through either of two credential modes — the coding-plan subscription or the metered API key — switch between them at will, and never lose a running session to a limit on the active mode or provider. The subscription mode is the daily driver, because its cost is already paid; the metered mode is the deep reserve. The pillar's promise is that no limit anywhere can stop work that the user has not chosen to stop.

Exact behavior demanded. The user holds both a coding-plan subscription and a metered API key for Z.AI — the same two credentials the Windows IDE uses, which proves both are valid and active. The app must support both modes simultaneously, meaning both are configured at all times, each with its credential stored under the same hardware-keystore encryption rules as every other secret in the app. At startup, and whenever a credential is changed, the app validates that each mode's credential is present and well-formed, and the provider chip reflects any gap honestly — a missing metered key, for instance, disables the metered mode rather than letting a session die later for a reason the app knew about in advance. The provider chip for Z.AI must expose a visible, immediate mode toggle between the two modes, usable at any moment, including while a session is running. Selecting the other mode takes effect on the session's next request without restarting the session, losing context, or re-creating anything — the conversation simply continues, billed or served through the other credential.

The failover contract is the core of the pillar. The millisecond any provider or mode hits a limit — a rate limit, an exhausted quota, or an unavailable server — the app must automatically move the running session to the next working mode or provider. The detection is per-failure, not per-minute: the failure response itself triggers the move, with no waiting for a timer to notice. The search order is fixed and deterministic: first between the two Z.AI modes (subscription to metered, metered to subscription), because staying on the same provider with a different credential is the smallest possible change; then across the other configured providers, including NVIDIA and OpenCode, in a stable order. A mode or provider that just failed is not retried again within the same failover pass until every other link has been tried, so the engine cannot ping-pong between two failing endpoints. Each hop must preserve the session's full context — the same conversation state, the same task, the same journal — so the continuation is seamless from the AI's point of view and from the user's. The session's model preference travels with it where the destination provider supports the same model, and falls back to that provider's default where it does not.

Every automatic switch writes a specific, dated journal line into the session recording what happened: which mode or provider hit the limit, what the failure was, and which mode or provider the session continued on. This line is both a user-facing explanation — the user watching the card understands why the status line changed shape — and the mission's primary acceptance evidence, since it is timestamped proof that the failover engine fired. The overarching guarantee: a session NEVER stops unless the user manually stops it. No limit, on any single mode or provider, may terminate a running session. If the entire failover chain is exhausted — every mode and provider simultaneously limited or down — the session enters an honest waiting state that says so, and resumes automatically the moment any link in the chain recovers; it does not mark itself failed. The waiting state itself emits a progress line when it begins and when it ends, so the card never goes silent.

How it works after the change. The user starts a session on the Z.AI subscription mode. The subscription hits its rate limit mid-run. Within one poll cycle, the journal shows a dated line recording the automatic switch, and the session continues on the metered key with no dialog, no restart, and no lost context. On a heavier day, the metered key is also exhausted; the session continues onward to NVIDIA, rotating keys per Pillar A, and if needed onward to OpenCode. The user watches the whole cascade as a sequence of journal lines and one uninterrupted, completing session.

Acceptance tests. First: a forced limit on one Z.AI mode triggers automatic continuation on the other mode within one poll cycle — meaning by the time the app's next sync cycle has completed, the session shows the switch line and has issued at least one successful request on the other mode. Second: manual mid-session switching works in both directions — subscription to metered and metered to subscription — with the session surviving each switch and the journal recording the mode change. Third: a cascade test — limits are forced across modes and providers such that the session cycles across at least four provider or mode configurations in one continuous run, and it completes successfully, with a dated switch line for each hop.

The edge cases and evidence for these tests are fixed in advance. For the forced-limit test, the edge cases are: the limit must be triggered while the session is genuinely mid-conversation, not between turns, so the transfer of context is actually exercised; and the switch must be timed — the timestamp on the failure and the timestamp on the first successful request on the other mode must sit within one poll cycle of each other. Evidence: the dated switch line, the poll-cycle timing read from the stamps, and a screenshot of the card showing the session continuing. For manual switching, the edge case is performing the toggle twice rapidly — the engine must serialize the switches rather than interleave them. Evidence: two journal mode-change lines and an unbroken run. For the cascade, the edge case is that each hop lands on a different model per the destination's default rules, and the closing line must name the configuration that actually finished the work. Evidence: the full dated sequence of switch lines read top-down from the finished card, one per hop, no gaps.

### Pillar C — live progress streaming for every provider and model

Goal. Make every running session visibly, specifically alive from start to finish, regardless of which provider or model powers it. A board full of running sessions should read like a control room: at any glance, the user can see what each piece of work is doing right now and when it last said something.

Exact behavior demanded. Every running session, from the millisecond it starts to the millisecond it finishes, must show fresh, specific, human-English progress at least once a minute. The timing contract has three parts. First, an immediate first update at session start — the user must see a progress line the moment the session begins, not sixty seconds later; the line names the model and provider and the stage the session is entering. Second, updates at most sixty seconds apart during the run — no gap between consecutive progress lines may exceed one minute, measured wall-clock between the stamps on the lines themselves. Third, a closing update at completion, stating that the session finished and what the outcome was, written at the moment of completion rather than on the next timer tick. The sixty-second progress broadcaster from section 3 is the backbone of this, but it must be extended so that it fires reliably for every provider and model combination, including NVIDIA under key rotation and OpenCode, and so that the first-update and closing-update moments are guaranteed by the session lifecycle itself rather than left to the timer's coincidence. The lifecycle hooks are explicit: the start hook writes the first line synchronously with the session starting, the timer owns the middle of the run, and the completion hook writes the closing line before the session's status is finalized.

The content contract is as important as the timing contract. Every line must describe the actual current situation: which model is running, which provider is serving it, what stage the work has reached, and what just happened since the last line. No two consecutive lines may ever be identical. No line may be generic filler such as a bare restatement of the session's name or a constant string; a line that could apply to any session at any moment is a failed line, because it communicates nothing the card's title did not already say. The line is written into the session journal with the standard progress marker and wall-clock stamp, so it appears at the top of the card and reads as natural English. When a provider fails over per Pillar B or a key rotates per Pillar A, the next progress line should reflect the new reality — naming the new mode, provider, or noting the recovery — which naturally satisfies the non-identical rule at exactly the moments it matters most. Where the session itself reports its steps, those reports feed the lines; where it does not, the broadcaster describes the observable state honestly — which stage the session is in, how long it has been running, what its most recent activity was — rather than inventing detail. The broadcaster must also keep the contract when the app is backgrounded and brought back: a run spanning a background gap shows the gap honestly in its stamps, and the next line after returning to the foreground lands immediately, restarting the at-most-sixty-seconds rhythm from the moment of return.

How it works after the change. The user starts any session on any provider. A progress line appears within moments naming the model and provider and the starting stage. Roughly every minute, another line appears, each one different, each one describing the latest real state: the stage advanced, a step completed, a failover happened, a key rotated. When the session finishes, a closing line lands. Reading the card top-down tells the whole story of the run without opening anything.

Acceptance tests. The behavior must be observed end to end on at least this set: Z.AI, at least two different NVIDIA models, and one OpenCode model. For each observed session: a first update appears immediately at start; every consecutive pair of updates during the run is at most sixty seconds apart; the closing update appears at completion; and every line in the sequence is distinct from its predecessor and specific to the moment — verified by reading the actual lines on the card. Any provider or model combination that fails the timing or content test is a defect to fix and retest, and the accepted set must be re-verified after every fix because the broadcaster and provider plumbing interact.

The edge cases sharpen the measurement. The timing check is done on a session long enough to produce at least five mid-run lines, so a single lucky pair cannot pass it. A very short session — one that finishes in under a minute — is a valid edge case with a stricter shape: first line at start, closing line at completion, and no mid-run lines required, but no gap violation possible either. The background case is tested deliberately: a session is started, the app is sent to the background for several minutes, the app is brought back, and the line appearing immediately on return plus the honest stamp gap proves the rhythm resumed rather than the timer having drifted while unobserved. Evidence per session: a screenshot of the finished card's full line sequence, with each adjacent pair's stamps checked against the sixty-second bound and each line read for specificity and difference from its predecessor.

### Pillar D — OpenCode model truth

Goal. Make the OpenCode model list always truthful: the picker shows exactly the models that exist on the service right now, and nothing else. Where Pillar A freezes NVIDIA's list by design, Pillar D does the opposite for OpenCode — the service, not the app, owns the list, because OpenCode's catalog changes on the service's schedule, not the app's.

Exact behavior demanded. The OpenCode model list must come only from the live models endpoint of the OpenCode service. The app must fetch the list from that endpoint — at app start and whenever the picker is opened or refreshed — and build the selectable model set exclusively from what the endpoint returns. Only models that exist right now may be displayed or selectable. Stale or unavailable models must vanish immediately: if the endpoint stops listing a model, that model disappears from the picker on the very next refresh, and it must not reappear through any cached or hardcoded path. This implies the removal of any hardcoded, bundled, or persisted model list that can disagree with the live endpoint; the live endpoint is the single source of truth, and any list stored anywhere in the app is at best a display cache with an honest label and never a selection source that outlives its freshness. If the endpoint cannot be reached, the app must show its honest state — the last known list clearly marked as possibly stale, or an explicit unreachable notice with a retry action — rather than silently presenting a list that may be wrong; selection from a marked-stale list may proceed but must be prepared to fail with a clear message if the service rejects the model. A session whose selected OpenCode model disappears from the live list between runs surfaces the change at the next start of that session — naming the vanished model and offering the current list — rather than failing opaquely. Restarting the app must not resurrect a vanished model, because the list is rebuilt from the endpoint on every start, and a model absent from the endpoint is absent from the picker everywhere.

How it works after the change. The user opens the provider chip, selects OpenCode, and sees the models the service currently offers — today that is three models. If the service adds a model tomorrow, it appears without an app update. If it retires one, it disappears on the next refresh. There is no scenario in which the user selects a model that the service will reject as unknown, except the narrow marked-stale offline case, which is labeled as such.

Acceptance tests. First: each of the currently live three models is selected in turn and runs a task successfully, three of three, evidenced by journal lines and completed cards. Second: the phantom test — the app is restarted, the picker is reopened, and the displayed set exactly equals the live endpoint's current set; this equality check is repeated after restart and after a network blip to prove no caching layer or stale storage ever reintroduces a model the endpoint no longer lists. The edge cases for the equality check are: the comparison is done twice in one session (picker closed and reopened must not change the set), and the set comparison is by exact membership both directions — nothing displayed that the endpoint lacks, and nothing at the endpoint missing from the display. Evidence: a screenshot of the picker beside the endpoint's current answer, plus the three completed cards.

### Pillar E — Delete All in the Finished column

Goal. Give the user a one-tap way to clear the Finished column entirely, in under one second, with no risk to anything else. Finished work is history; the user should be able to archive it away in a glance, not spend a minute tapping cards one by one, and never worry that the button could eat live work.

Exact behavior demanded. The Delete All button removes every task in the Finished column — and only there. Its scope is fixed at construction time: the set of tasks to delete is computed as exactly the tasks currently in the Finished column, snapshotted once at the moment of confirmation, and no task in To do or In Progress is ever included, no matter how the board is filtered, sorted, or scrolled. Tasks created in other columns between the confirmation tap and the deletion completing are not in the snapshot and are therefore untouched by construction, not by luck. The deletion must complete in under one second even with dozens of tasks, which demands parallel deletion: the delete requests are issued concurrently rather than one at a time, so the total time is governed by the slowest single delete rather than the sum of all of them. Concurrency is bounded to a sensible width so the burst does not trip the server's own protections, and any individual delete that fails transiently is retried through the app's normal retry path within the same run. A delete that ultimately fails after retries is reported honestly when the run ends — with the count that succeeded and the identifiers of anything left behind — never silently swallowed.

The interaction has three safeguards. First, one confirmation step: the first tap shows a confirmation stating exactly what will happen — the number of Finished tasks that will be deleted — and deletion proceeds only on confirmation. One step, not a maze; the count in the dialog is taken from the same snapshot that the deletion will use, so the dialog never lies. Second, visible progress: during the deletion the user sees that it is happening and, when practical, how far along it is; the deletion is never a silent freeze. Third, double-tap protection: once a deletion run has started, further taps of the button are ignored until the run completes, so an impatient second tap can never launch a second overlapping deletion pass. After the run, the Finished column is empty, the deletions have been pushed through the normal retry and conflict-detecting sync path so they propagate as proper tombstones to every other client of the workspace, and the board re-renders cleanly with no ghost cards and no scroll jumps. Deletion here is permanent by design — the user confirmed it — and no undo is promised or shown.

How it works after the change. The user finishes a long day with forty completed sessions cluttering the Finished column. One tap, one confirmation naming forty tasks, a brief visible sweep, and within a second the column is empty while the To do and In Progress columns are untouched and the deletions sync everywhere.

Acceptance tests, with concrete numbers. The test seeds at least thirty finished tasks and places guard tasks in both other columns — at least one in To do and one in In Progress. The test then runs the Delete All flow three consecutive times (re-seeding between runs). Each run must complete in under one second from confirmation to empty column, must delete every seeded finished task, and must leave every guard task in place — zero collateral deletions across all three runs. The double-tap protection is exercised by tapping repeatedly during a run and confirming only one deletion pass occurs.

The edge cases and evidence are fixed in advance. The timing is measured from the confirmation tap to the moment the column renders empty, using the app's own log timestamps rather than a stopwatch, so the number is honest. A task moved into Finished in the final instants before confirmation belongs in the snapshot; a task created in To do during the run must survive — both are exercised by staging the moves deliberately. Propagation is verified by checking that the deleted tasks are gone after a fresh full pull, proving the tombstones landed on the server rather than merely hiding cards locally. Evidence per run: the log window showing start and end stamps for the deletion pass, the before and after screenshots of the board with guard tasks visible, and the confirmation dialog's count matching the seeded number.

## 5. THE FULL AUDIT

Once all five pillars pass, the mission moves to a complete audit: every screen, chip, button, dialog, and setting in the app must be exercised on the real phone, by hand, with evidence. No control is exempt, including controls that "should" work because nothing nearby changed — the audit exists precisely to catch the interactions nobody reasoned about, the combination effects where two features meet: a failover happening while the user is mid-gesture on the same card, a delete-all finishing while a sync pull is in flight, a key cooldown expiring while the key screen is open.

The audit inventory covers, at minimum, the following areas, each of which must be walked item by item. Pairing: the flow that links the app to the workspace, from a fresh state if possible, including failure handling on a wrong key. Sync key display: wherever the app shows its pairing or sync key, confirm it matches the real key, is masked or revealed only by explicit user action, and never leaks into logs or screenshots of other apps. Column moves: moving cards among To do, In Progress, and Finished in every direction, confirming the move lands on the server and survives a pull. Card actions, one by one: complete, reopen, pause, resume, message (sending a message line into a session's journal and seeing it appear), order (issuing an order line and seeing the intended effect), model switch (covered under Pillar A's mid-run test, but also exercised in idle state), provider switch (including both Z.AI modes per Pillar B), and retry (forcing a failed action and confirming the retry path recovers). Delete All: the full Pillar E flow, re-confirmed here as part of the whole. Watchdog behaviors: confirming watchdog heartbeat lines are written on schedule and that the hero display correctly ignores them, per the parser rules in section 3. Reminders: any reminder or notification feature, triggered and dismissed on device. Settings: every settings entry opened, changed, and reverted, confirming each takes effect and persists across a restart. Key management: the Pillar A key screen fully exercised — add, remove, states, masking — plus the Z.AI mode configuration.

Each inventory item carries an expected-behavior statement that the tester checks against, not just a tick box. For column moves, the expectation is three-fold: the card renders in the destination column within one poll cycle, the move survives a kill and relaunch of the app, and a journal line records the move. For complete, the card's status changes, the journal gains a dated line, and the completion is visible after a full pull from another reading of the workspace. For reopen, a finished card returns to To do with its journal history intact — reopening must not truncate or rewrite the description. For pause and resume, a paused session stops producing progress lines within one broadcaster tick of pausing and resumes the rhythm within one tick of resuming, and both transitions are journaled. For message and order, the line appears at the top of the card with the correct marker and stamp, and in the order case the intended effect is observable — the session acknowledges with an ack line. For retry, the failure is staged deliberately, the retry is observed succeeding, and the journal shows no duplicate of the retried write. For watchdog behavior, heartbeats appear in the journal at their expected interval while the card's headline status remains a human-authored line, never a heartbeat. For settings, every change is verified to have an observable effect — a setting that changes nothing observable cannot be marked pass, only marked as unverifiable and investigated.

Method: for each inventory item, the tester performs the action on the phone and records a pass or fail with evidence — a screenshot, a runtime log line from the app's own tag, or the visible journal line on a card. The inventory is written down before testing starts, so that "everything" has a definite, checkable meaning and nothing is skipped because it was forgotten. Anything that fails is fixed in source, rebuilt, reinstalled, and retested from the start of that item's flow, not from the point of failure — a fix can disturb the earlier steps of its own flow. Because a fix can also disturb its neighbors, each fix triggers a targeted regression pass over the pillar it belongs to, and the full audit's passing set is re-confirmed at the end. The audit is complete only when every item shows a passing result with evidence recorded against it.

The final act of the audit, after the last fix lands, is recompiling the app icon so the installed icon reflects the final state of the project — a deliberate last build that also serves as one final full identity-checked install and launch.

## 6. BUILD, INSTALL, AND VERIFICATION DISCIPLINE

Every change reaches the phone through one path, and every claim of success is backed by one kind of evidence. This section defines both.

The build runs on the Windows machine using the contained toolchain: JDK seventeen, Gradle eight point nine, and Android SDK thirty-four. The build invokes the companion package target with the web client prebuilt flag, so the embedded web assets are not rebuilt from scratch on every Android build — the prebuilt web client is packaged as-is. The output is the companion debug package, signed with the escrowed keystore created during the foundation phase. Three escrow copies of that keystore exist in separate locations, and before any signing build the session may confirm the escrow copies still exist — a signed build made with the wrong or a missing keystore is a wasted cycle at best and an accidental uninstall trigger at worst. The keystore is never regenerated under any circumstance: regenerating it changes the signing identity, a mismatch with the installed app forces a full uninstall and reinstall, and a full reinstall means the app's local data is lost and the pairing must be redone. Losing the keystore once already cost the project a forced fresh install; the rule now is absolute.

After each phase of work, the cycle is always the same: rebuild, install over the top of the existing installation (which the escrowed keystore makes possible), relaunch the app, and confirm the specific change landed live. The user must SEE each change land — a changed screen, a new control, a new journal behavior — not be told it changed. An install that cannot be visually confirmed did not happen. Install-over-top is itself a verification point: if the install reports a signature mismatch, something has gone wrong with the keystore path, and the session stops to investigate rather than uninstalling through the failure. After a relaunch, the app is given a moment to complete its first sync, and the board is confirmed to be showing live data before any test begins — testing against a half-loaded board produces false failures that cost more time than the wait.

Verification is on-device or it is nothing. Source-level tests, unit results, and code reading may guide development, but nothing may be claimed done from a source-level test alone. The accepted forms of evidence are: foreground checks, confirming the app in the foreground is the companion package running AiWorkspaceActivity; package listing, confirming the companion identifier is installed and the removed variants remain absent — this is the identity re-verification demanded in section 1, performed before acting on the phone; runtime logs filtered to the app's own tag, showing the internal events matching the behavior under test; screenshots of the actual screen state; and the journal lines themselves, visible on the session cards, which are the app's own honest record of what it did. A test result that rests on any other form of evidence is not a test result. Each pillar's gate closes only when its acceptance tests, run through this cycle, have all passed with evidence recorded.

## 7. OPERATING RULES

These rules bind every working session on this mission, from the first minute to the last.

Never stop, sleep, idle, or drift until every gate is green. Long-running waits — builds, installs, cooldown timers — are monitored actively, and the moment each finishes, the next step begins. The mission advances continuously or not at all; there is no mode in which a session waits passively for something to happen. Applied concretely: while a build runs, the session prepares the next test's seed data; while a sixty-second key cooldown elapses, the session watches the key screen for the recovery moment rather than wandering to unrelated work; when an install finishes, the launch and foreground check happen immediately, not after a pause.

Update the visible tracker the instant a test passes. The tracker is the shared, at-a-glance record of pillar and audit status. A passing test that is not recorded within moments of passing is a source of confusion and repeated work. The tracker is updated first; celebration, analysis, and the next step come after. Applied concretely: the moment the fifth of five NVIDIA model runs completes, its tracker row is marked green with its evidence reference before the session so much as begins analyzing the result — a pass that exists only in a scrollback is treated as unrecorded.

Never touch the normal Daymark app or any other package. The identity lock from section 1 applies to every action without exception: verify the companion identity via package listing and foreground checks before every build, install, launch, and test; if the target of any action is ambiguous, stop and re-verify. The normal Daymark tasks app is outside this mission's universe permanently. Applied concretely: if a log line, a process listing, or a screen shows a name that could belong to either product, the session does not guess — it resolves the exact package identifier first, and only then acts.

Never store a secret in plaintext or logs. Every API key, pairing key, and token lives only in hardware-keystore-encrypted storage. Logs, screenshots, exported files, and test fixtures must be inspected to ensure no secret material appears in them. When evidence requires showing key state, show masked state. Applied concretely: a screenshot of the key-management screen is only evidence if every key reads as masked or positionally labeled; a log excerpt is only admissible if any credential-shaped string has been redacted before it is recorded anywhere.

Never claim success without on-device proof. Section 6 defines what proof is. A build that compiles is not a pass. A unit test that passes is not a pass. Only observed behavior on the phone, evidenced by foreground checks, logs from the app's tag, screenshots, or visible journal lines, may be recorded as a pass. Applied concretely: "the rotation logic is correct because the code handles it" is never a tracker entry; "key three was rejected, the session continued on key four without an error dialog, and the key screen showed the cooldown" is.

Treat every user demand as equally binding from the first to the last. There are no low-priority requirements in this mission. A demand the user states in passing carries the same obligation to be implemented, tested, and proven as the largest pillar. The mission is done when the pillars are green, the audit is green, and every demand the user has made — in this document or outside it — is satisfied with evidence.

## 8. PHASED EXECUTION ORDER

The work proceeds in fixed phases, each closed by an explicit gate, so that progress is always measurable and nothing is left half-verified.

Phase one is identity and baseline: re-verify the companion package is the installed and foreground app, confirm the removed variants stay absent, confirm sync pulls and pushes against the user's own backend still succeed, and record the baseline state of every screen before changes begin. Gate: identity checks green and baseline recorded.

Phase two is Pillar A, the NVIDIA key pool and model lineup, because its rotation engine and key-management screen become infrastructure that Pillar B's failover chain depends on. Gate: all four Pillar A acceptance tests pass with on-device evidence.

Phase three is Pillar B, Z.AI dual mode and the failover chain, built on the now-stable NVIDIA provider and OpenCode as chain links. Gate: the three Pillar B acceptance tests pass, including the four-hop cascade.

Phase four is Pillar C, universal live progress, which must be verified across the provider landscape established in phases two and three. Gate: the timing and content contract passes on Z.AI, at least two NVIDIA models, and one OpenCode model.

Phase five is Pillars D and E together, the OpenCode truth list and the Finished-column Delete All, both self-contained. Gate: the three-model OpenCode run and phantom test pass, and the three-run Delete All test passes with zero collateral deletions.

Phase six is the full audit of section 5, with fixes folded in as they are found and the regression passes they demand. Gate: every inventory item passes with evidence.

Phase seven is closure: final regression over all five pillars' acceptance tests against the final build, the app icon recompiled, one last identity-checked install and launch, and the visible tracker marked complete. Gate: everything green, on the record, on the phone.
